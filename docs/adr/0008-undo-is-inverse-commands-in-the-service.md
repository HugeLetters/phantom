# Undo is a stack of inverse commands, kept by the service

Remove and Delete act at once (⌫, ⌘⌫), so ⌘Z takes back the last of them (#150). What a Remove or a Delete changed is kept as what it takes to reverse it: the torrent's record (its id, destination, what's wanted, its seeding round), its .torrent and librqbit's `.bitv` (the pieces it had), hard-linked from the session folder while the torrent is still whole, with each of its files as it was then, and for a Delete each item it moved with where the Trash put it (`trashItemAtURL`'s resulting URL) and what it was there (volume and inode, and a file's length and modification time), recorded as each goes, in the write-ahead record a Delete under way already has. An undo is a command of its own: it puts back from the Trash what Delete moved, only what's there as it went, never over anything at the path, never through a symbolic link, and inside the destination only; then it adds the torrent again from what was kept, under its id. The pieces it had come back with it, without a full check, only while every file is as it was when it was kept (a rename to the Trash and back keeps it so); a file written or replaced since makes librqbit check them all, as librqbit itself only notices a file it can't read. One removed or deleted while Unchecked (its check cancelled, #88) comes back Unchecked, as it does after a restart: nothing checked its pieces. Like any command it can be refused with a typed reason the client words: the Trash was emptied, something is at the path, a folder on the way is a link, the drive isn't connected, the torrent was added again (the app says only "Already in the list": nothing was touched).

The stack lives in the service, kept in the data dir next to the store (`undo.json`, and a folder per kept torrent): one stack whatever made the change, so `phantom undo` works, and it outlasts the app and the service restarting. It's 20 deep; the oldest goes. It's a machine (`lifecycle::undo`, which the GUI's fake runs too): an Undo takes the top entry off the stack at once, and it's under way until it ends, carried out or not. An Undo asked while one is under way (⌘Z pressed again, the notice's Undo, `phantom undo`) waits its turn rather than being refused: the machine counts those queued, never more than the stack holds (a press beyond that is nothing to undo), and each takes the then-newest entry once the one before it ends, answering its own client. A stop leaves the queued ones unrun. An undo that runs past a second shows "Undoing…" in the status bar until the last ends. Remove, Delete and Move to Trash (below) are on it; Pause, Resume, a priority, Add, Check and the settings aren't, and there's no redo.

**A refused undo is dropped, not kept.** Most reasons never fix themselves (an emptied Trash, a torrent added again, a file put where one goes back), and one that stayed on top would hide every older entry behind it, so ⌘Z would keep saying the same thing. Telling the reasons that may pass (a drive away) from the rest would be a rule per reason. Nothing is lost but the shortcut: the notice says why, and the files are still in the Trash, where Finder's Put Back works. An undo that can't finish once it's begun (a move back failing, or adding the torrent again failing once its files are back) returns what it moved to the Trash first, so every undo does all or nothing, and a refused one has changed nothing. What can be told before anything moves is (every item in the Trash as it went, each path free, the folders on the way real ones, the destination there and named, the .torrent kept readable), so the rest is rare; what then can't go back to the Trash is named in the refusal.

Every step is written ahead: what brings a torrent back is in `undo.json` before its record leaves `engine.json`, and the undo under way before anything moves. An undo under way when Phantom stops is finished first; one cut short by a crash is finished at the next start, and a partly deleted torrent still in the list is taken out then. An item no longer in the Trash is one it put back, if it's at its path as it went; otherwise it was emptied from the Trash meanwhile and, while its path is free, stays gone, and its files download again (#162). An item that then can't go back (something is at its path, an emptied one's too, or a folder on the way is a link) ends the undo as any undo that can't finish ends: what it put back goes to the Trash again, including what went back before the crash, and the undo is refused. A Delete whose torrent the crash left in the list with all its files gone is taken off at the start, its entry written again in its own place. So is a Remove the crash cut short between those two saves, with the entry and the stash it kept then (#162). An add of the torrent an undo is bringing back waits for it. `undo.json` never keeps the service from starting: what can't be read (a newer build's entry, a broken file) is dropped, entry by entry, and the file kept beside it as `undo.invalid.json`.

In the app, Remove and Delete each tell what they did in the status bar ("Deleted Album"), its popover with an Undo of that action, on while it's the newest on the stack. ⌘Z and Edit ▸ Undo (macOS's standard item, which hands the key to the window) undo the last, whatever made it.

## Move to Trash is on the stack too (#151)

⌘⌫ on selected files sets them Off, then moves those on disk to the Trash (that order, so a size check never finds a file the torrent gets gone), on the trashing a Delete uses. It's one undo step per ⌘⌫: an entry whose torrent stays in the list (`Back::Files`), with the items it moved (as a Delete's) and each file asked about with the priority it had. An Undo puts back from the Trash what's still there, and each file's priority as it was, in the same all-or-nothing way (a failure puts back what had come back); the rules of the stack stand: it lives in the service, a refused undo is dropped, one that has nothing to put back (every item gone from the Trash) is refused as any is.

**A partly emptied Trash restores what's left.** Unlike a Delete's, which brings back a torrent whole or not at all, a Move to Trash is made of independent files: one emptied from the Trash doesn't make the others unrecoverable. Each file still in the Trash goes back, and gets its previous priority; one that was moved and isn't there stays Off (Normal would make it Missing files), and the rest of the files asked about get theirs.

**Cut short by a crash**, an undo of a Move to Trash is finished at the next start by the same rule as any (#162): what's still in the Trash goes back (an item emptied from it meanwhile stays gone while its path is free), and priorities are restored; with something of the user's where an item goes back, nothing is put back, what had gone back before the crash returns to the Trash, and the undo is refused and dropped. Commands for its torrent wait for it as they do for a running one.

Its torrent must be in the list, the same one (added again since is another), and one that moving files to the Trash would do something to now (not deleting, not partly deleted, destination reachable): the lifecycle's own answer, in the words of Undo. It takes the place of no entry and none takes its: the torrent never left, so it's a step of its own. It's written to the stack once the move has ended, not ahead as a Delete's items are: a crash in between leaves the files in the Trash and Off, never half restored, and costs only the Undo. While one runs, every Remove, Delete and Move to Trash (of any torrent) and every Undo waits, and so does any other command for its torrent: entries go on the stack in the order the commands came, and an Undo takes back the last action, not the one before a move that's still going. The same holds for the torrent's commands while an Undo of its Move to Trash puts files back (the torrent stays in the list, so nothing else would hold them). What waited runs, in order, once it ends; a stop doesn't run it: each is answered that the service is stopping. The undo sets the priorities Off first and Normal last, so one that fails halfway never leaves a file Normal that it then moves back to the Trash.

## Considered options

- **An event log replayed backwards.** librqbit and the disk can't be replayed or rewound: the files move, the Trash renames them, librqbit forgets the pieces with the torrent. An entry that knows how to reverse its own action is what can be carried out, and checked against the disk as it is now.
- **The stack in the GUI.** Each client would keep its own, lost when the app quits, and the CLI's actions couldn't be undone from the app or the other way round. The service already owns the torrents and the Trash's records.
- **Keeping a refused undo.** See above.
- **Finishing an undo cut short with what's back** (#162): adding the torrent again with the items put back before the crash, and the ones blocked since showing as Missing files. A blocked item is blocked because of what's at its path, or a link on the way, and adding the torrent again would have librqbit write its file over that, or through the link. Making that safe would need a torrent kept in the list that never touches some of its own paths. An undo after a crash does what any other undo does instead. Only an item emptied from the Trash, whose path is free, is left out.
- **Adding the torrent again from its .torrent alone.** librqbit then checks every piece. Keeping its `.bitv` brings it back with its progress; librqbit still reads a piece of each file it says it has, so a file that's gone makes it check them all.
