# Look Presets: a theme and its settings per Appearance

The look of the app is a **Look Preset**: a **Theme Look** (a theme with its settings) for the Light Appearance and one for the Dark Appearance. The system's Appearance only picks which of the two is shown; a theme declares nothing about it, and there is no Palette layer. A variant such as Persona 3 Reload's Dark Hour is a theme setting or another theme.

Each Theme Look stores its own theme id and settings, so a Look Preset is two full values, often equal. Every theme setting can differ between the two Looks. When both use the same theme the settings screen shows one set of fields and writes both; splitting a field (the Theme choice too) is only a client shortcut for setting it on each Look separately, and a field shows as split when the two values differ. Joining one whose values differ copies the Light value into Dark. With a different theme in each half there is nothing to join: the editor shows two independent lists, each starting with its own Theme choice. Nothing is stored per theme outside a Look Preset, so switching a Look's theme starts at that theme's defaults.

The app shows an **Active Look Preset**, a working copy, kept in the GUI's `gui.json`. Saved Look Presets are named snapshots: applying one copies it into the active one, tweaking leaves it alone, and the user can update it or save a new one. A saved preset's half can be copied into just the Light or the Dark Look, so mixing halves is possible; that is why the active preset can't be a saved one edited in place. A fresh install has Phantom with the Tone setting, Light in Light and Dark in Dark.

Settings shows the presets as rows, the Active look's first (its Edit… and Save as…, no Apply or Delete) and then each saved one's, each with a chip for each half and one for both that applies it (◐ both, ☀ Light, ☾ Dark). Which half is in use is worked out by comparing values with the Active look's, never remembered, so it stays true after any edit. One editor sheet edits a Look Preset: the Active look's edits are its real settings, a saved preset's are drawn live in both windows as a transient override and kept only in that saved preset, so the Active look is never touched by looking at a saved one. Every Apply, save, replace and delete is one step of Undo ([ADR 0008](0008-undo-is-inverse-commands-in-the-service.md)) that puts the Look Presets back whole, and so is the editor sheet's Done, whatever was changed in it ("Edit of Night"); an Apply's focuses the chip that was used. Inside the sheet, ⌘Z takes back its own changes one at a time, each reopening the control it set, and nothing older; its Cancel puts the preset back as it was when the sheet opened and leaves none of its changes to undo. The sheet has two columns, ☀ Light and ☾ Dark, each drawn in their half's look, as if the system were set to that Appearance, with one hairline per row across both. With one theme in both halves each row is a pair of cells: a joined row's control sits in the left column and its right cell is blank; a split row has one control in each; a Join or Split button on the row turns one into the other. With a theme in each half the columns are two lists. Cancel and Done end the sheet; Done is one undo step.

A theme declares its settings as typed descriptors: a key, a label, a default and a kind from a small closed set (toggle, choice from a fixed list, color), and optionally the section and group Settings shows it in; Phantom declares `tone` (Light, Dark), Corners, Motion and its Colors. A color holds nothing until it's set by hand: the theme works it out, from the setting it follows (a base color) or its own default for that Tone, and tells Settings what it came to and any warning about it; only a color set by hand is stored. One generic settings screen shows them. Values are stored as JSON by key. Each half is repaired from what a fresh install has for that half: a value of the wrong kind, or missing, comes back as a fresh install's half has it (so a Dark half's Tone comes back Dark; the theme's default when that half is another theme's), an unknown key is dropped, a half naming no theme there is comes back as a fresh install's half, and an unreadable preset as a fresh install's; what was reset is named in the settings-reset notice. A new kind is added when a theme needs it.

Given a Theme Look's settings, a theme builds a resolved look: tokens, block overrides (a button, a table row, a context menu), optional screen overrides (a wholly different torrent info panel), and the app icon as image bytes. The app keeps two resolved looks, one per Appearance, and a settings change rebuilds only the one it touches. ADR 0004's parent fallback is unchanged: a block the theme doesn't draw resolves through theme, parent, Phantom.

There is no control to pin the Appearance. Using the same Theme Look for both Appearances is the pin; the cost is that a temporary "always Dark" overwrites the Light half unless a preset was saved first. An Appearance override (System, Always Light, Always Dark) on the Active Look Preset can be added later without changing the model.

The **App icon** is not part of a Look Preset. It is one global setting, one icon or a Light and a Dark icon, or follows the theme, which means the icon the Theme Look for the current Appearance gives, possibly rendered from its settings. A deliberate icon choice therefore survives changing preset or theme. It is chosen in its own sheet, which keeps the undo rules of the editor's ([ADR 0008](0008-undo-is-inverse-commands-in-the-service.md): one session per sheet; its Done is one step, "App icon: <old> → <new>"), from the shipped icons, the designed pairs (a dark and a light icon made to go together, which set both halves at once) and images the user adds; each half can also follow the theme alone. Added images are stored by path and read where they are, of any size, off the main thread and scaled to icon size (1024 px on the long side, never up) as they're read, so only the scaled image is kept and drawn, whatever the original's size or format: at launch the window opens at once, a half naming an image that isn't read yet shows the theme's icon until it is, and its tile is a placeholder. A file that doesn't decode as an image is refused when added.

## Stored data

In `gui.json`, with no migration: an older file may be reset, and an older build drops what it doesn't know. `app_icon` may hold `{"icon": id}` or `{"dark": id, "light": id}`, where either half may be `"theme"` (follow the theme alone) or a `file:/path` id; a new key, `app_icon_images`, lists the added images' `file:` ids in the order they were added. `app_icon_settings` holds the settings of the icons a theme draws, by icon id and half, only those not at their default: `{"phantom": {"light": {"tile": "follow"}, "dark": {"tile": "#3f7ed0"}}}`, a color being `"original"`, `"follow"` or `"#rrggbb"`; anything invalid resets the key, named in the settings-reset notice. The Look Preset's shape is unchanged.

## Considered options

- **Palette layer under each theme**: a third axis next to theme and Appearance; everything it does a theme setting can do.
- **Settings stored once per theme id**: keeps values across switches but can't express a different theme in each Appearance with its own settings, and hides what is shown behind a lookup.
- **Flat themes only (Plain Light, Plain Dark…)**: no shared settings between a family's members; changing "animations off" means doing it twice.
- **Editing saved presets in place**: simplest, but can't represent a mix of halves taken from different presets.
- **Remembering which saved preset (or half) the Active look came from**, to show "in use": it goes stale as soon as the Active look is tweaked or a saved preset is replaced. Comparing values needs nothing stored.
- **An inline editor for the Active look beside the sheet for saved presets**: two editors for one job. The Active look's row opens the same sheet, whose edits are real settings.
