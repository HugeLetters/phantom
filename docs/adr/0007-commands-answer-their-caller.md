# Commands answer whoever sent them; only live data is an event

The GUI's seam to the service has two kinds of traffic, and they get two shapes. A command (add, pause, remove, set priority…) takes a completion, `done: Box<dyn FnOnce(&mut Phantom, Result, &mut Tx) + Send>`, and its result runs that closure, so the code that sent the add decides what its answer does: the link field clears on success, or keeps its text selected on failure. Live data (the listing, the watched torrent's details, the connection) keeps arriving through `poll`. Both reach the UI thread through one ordered queue that Rune's `poll` drains once per frame: `Incoming::Live(..)` is applied to the state and `Incoming::Answer(f)` is called. Because it's one queue, the listing that shows an added torrent still comes before the add's answer. This is the "ask" pattern the engine's actor already uses (ADR 0006), and it matches Rune's own idiom of closures on the state (`AppHandle::update`, `Tx::element_at`). Request ids exist only where a thread boundary needs them, inside `SocketService`, and the app never sees them. `MemoryService` keeps `(due, answer)` pairs and releases them on the virtual clock, so tests stay deterministic.

This removes the `adding` flag, `RequestId` and `last_request`, `Event::Added`, `AddFailed` and `NoDestination`, which becomes `AddError::NoDestination(source)` in the add's own result. It also removes the service's `Notice` events: only answers and the connection set the notice.

## Considered options

- **Fire-and-forget commands with answers as events** (the previous design): the app has to rebuild which answer belongs to which request, using flags or app-made request ids, so every new caller needs another branch.
- **Answers as tagged messages, as in Elm or iced** (`Message::LinkAdded(Result)`): this works, but Rune has no message-and-update loop; its handlers are closures on the state, so a message enum would be one more layer to route through.
- **An async `Stream` or futures for answers:** Rune has no executor. The frame loop and `AppHandle::wake` already poll and wake, so a stream adds a dependency and no behaviour.
- **`AppHandle::update` directly from the socket threads:** this is the closest fit to Rune, but tests drive a bare `Runtime` with no `AppHandle`, and the fake answers on the app clock. Sending answers through `poll` keeps one path for both implementations.
